# repository-format Specification

## Purpose

The on-disk contract of a review repository: its governing principles, its
directory layout, which files are authoritative versus derived, and how the
format is versioned and migrated. The repository format is the contract; the
CLI, the web UI, and any future reimplementation are interchangeable as long as
they honour it.

Rationale and worked examples: [design.md](design.md).

## Requirements

### Requirement: Plain text, always

Every authoritative file MUST be UTF-8 text with LF line endings and a trailing
newline. The repository MUST NOT use binary formats, databases, or proprietary
containers for authoritative data.

#### Scenario: Inspecting a repository without strata

- **GIVEN** a review repository
- **WHEN** every authoritative file is opened with `cat`
- **THEN** each is readable UTF-8 text with LF endings and a trailing newline

### Requirement: The event log is the truth

Anything that can change MUST be stored as an append-only event. Nothing is
edited in place except human-authored prose (protocol, notes) and declarative
configuration (criteria, schemas, analyses).

#### Scenario: A reviewer changes their mind

- **GIVEN** `ethan` included a record
- **WHEN** `ethan` later excludes it
- **THEN** a new event is appended and the earlier event remains in the file

### Requirement: Derived files are committed but never read as input

Computed views MUST be regenerated deterministically and committed, so a
`git diff` shows what a change did to the review. They MUST never be read back
as input.

#### Scenario: Derived file deleted

- **GIVEN** `derived/pool.tsv` has been deleted from the working tree
- **WHEN** any command that folds the event log runs
- **THEN** it succeeds, because no state is read from derived files
- **AND** the file is regenerated

### Requirement: Merges must be boring

File layout and merge drivers MUST be chosen so that the normal collaborative
operation — two people screening the same records — produces zero git
conflicts.

#### Scenario: Two reviewers screen the same records

- **GIVEN** `ethan` and `sam` each screen the same 2,000 records on separate clones
- **WHEN** their branches are merged
- **THEN** git reports no conflicts

### Requirement: Directory layout

A review repository MUST use this layout (files marked GENERATED are produced by
`strata` and MUST be reproducible from authoritative inputs):

```
my-review/
├── strata.toml                  # project manifest and configuration
├── protocol/
│   ├── question.md              # research question, PICO(TS), rationale
│   ├── criteria.yaml            # inclusion/exclusion criteria (versioned)
│   ├── moderators.yaml          # planned moderators and their coding
│   ├── outcomes.yaml            # outcome definitions
│   ├── searches/<id>.yaml       # one file per executed search
│   └── amendments.md            # GENERATED: protocol change log
├── imports/<import-id>/
│   ├── manifest.yaml            # what was imported, from where, hashes
│   └── raw/<export-file>        # untouched export, source of truth
├── records/
│   ├── records.ndjson           # canonical bibliographic records
│   └── aliases.ndjson           # absorbed-id -> canonical-id
├── events/<domain>/...ndjson    # append-only, sharded by stage and actor
├── extraction/                  # coding form, per-reviewer and consensus records
├── rob/                         # instrument and per-reviewer assessments
├── analysis/<id>.yaml           # declarative analysis specifications
├── analysis/results/<id>/       # GENERATED
├── derived/                     # GENERATED, committed, never read as input
├── reports/                     # GENERATED
├── fulltext/manifest.ndjson     # GITIGNORED directory except the manifest
├── .strata/hooks/               # versioned git hooks (core.hooksPath)
├── .strata/schema-version       # format version, e.g. "1"
├── .strata/cache/               # GITIGNORED: fold cache
├── .gitattributes               # GENERATED by `strata init`
└── .gitignore                   # GENERATED by `strata init`
```

`strata verify` MUST regenerate GENERATED files into a temporary directory and
fail if the result differs from what is committed.

#### Scenario: Freshly initialised repository

- **WHEN** `strata init` creates a repository
- **THEN** `strata.toml`, `protocol/`, `records/`, `events/`, `.strata/schema-version`,
  `.gitattributes`, and `.gitignore` exist in the layout above

#### Scenario: Committed derived file edited by hand

- **GIVEN** a hand edit to a committed file under `derived/`
- **WHEN** `strata verify` runs
- **THEN** it reports the drift and fails

### Requirement: Authoritative versus derived files

Files MUST follow this authority, commit, and edit policy:

| Path | Authoritative | Committed | Editable by hand |
|---|---|---|---|
| `strata.toml` | yes | yes | yes |
| `protocol/**` except `amendments.md` | yes | yes | yes |
| `protocol/amendments.md` | no | yes | no |
| `imports/*/raw/**` | yes (immutable) | yes | never |
| `imports/*/manifest.yaml` | yes | yes | no |
| `records/records.ndjson` | yes | yes | discouraged |
| `records/aliases.ndjson` | yes | yes | no |
| `events/**` | yes (append-only) | yes | never |
| `extraction/**`, `rob/**` | yes | yes | yes |
| `analysis/*.yaml` | yes | yes | yes |
| `analysis/results/**` | no | yes | no |
| `derived/**` | no | yes | no |
| `reports/**` | no | yes | no |
| `fulltext/manifest.ndjson` | yes | yes | no |
| `fulltext/*.pdf` | — | **no** | — |
| `.strata/cache/**` | no | **no** | no |

Hand-editing an append-only event file is a data-integrity error, and
`strata verify` MUST detect it via per-event digests and refuse to proceed.

#### Scenario: Event file opened and saved in a spreadsheet

- **GIVEN** a collaborator opens `events/screen/title-abstract.sam.ndjson` in Excel and saves it
- **WHEN** `strata verify` runs
- **THEN** it reports `E_CHAIN` at the first altered line and exits non-zero

### Requirement: Format versioning

`.strata/schema-version` MUST hold a single integer, and `strata.toml` MUST
record the `strata` version that created the repository.

- A tool reading a repository with a **higher** schema version than it supports
  MUST refuse to operate and say so (`E_SCHEMA_TOO_NEW`, exit code 6).
- A tool reading a **lower** version MUST offer `strata migrate`, which performs
  the upgrade as an ordinary commit with a generated message, and MUST NOT
  migrate implicitly.
- Migrations MUST be forward-only, idempotent, and MUST NOT rewrite history.
- Adding an optional field to an event body is not a schema bump. Changing the
  meaning of an existing field, the normalisation rules, the fold, or the
  canonical serialisation is.

#### Scenario: Repository from a newer strata

- **GIVEN** `.strata/schema-version` contains `2` and the tool supports up to `1`
- **WHEN** any command runs
- **THEN** it refuses with `E_SCHEMA_TOO_NEW` and exits with code 6

#### Scenario: Repository from an older strata

- **GIVEN** a repository at schema version 1 and a tool at version 2
- **WHEN** a command runs
- **THEN** the tool offers `strata migrate` and does not modify the repository on its own

#### Scenario: Migration run twice

- **WHEN** `strata migrate` is run twice
- **THEN** the second run makes no changes and creates no commit
