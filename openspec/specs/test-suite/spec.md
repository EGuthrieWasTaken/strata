# test-suite Specification

## Purpose

How correctness is proven: the test levels and coverage floors, the identified
property invariants (P1–P13) and end-to-end scenarios (E2E-01–E2E-12), golden
parser fixtures, statistical validation against `metafor` and published worked
examples, fuzzing, performance regression, usability testing, and the rule that
every change carries its tests, with requirement traceability.

Rationale: `docs/spec/14-testing.md` §1–§8, §10.

## Requirements

### Requirement: Test levels and coverage floors

The suite MUST include unit, property, golden, statistical, integration,
end-to-end, performance, fuzz, cross-platform, and manual (usability) levels.
Line coverage MUST be at least 90% overall, and branch coverage MUST be 100% in
`core/fold.py`, `core/ids.py`, `core/canon.py`, `protocol/staleness.py`, and
`stats/escalc.py`.

_Source: `docs/spec/14-testing.md` §1_

#### Scenario: Uncovered branch in a critical module

- **WHEN** a change leaves one branch in `protocol/staleness.py` uncovered
- **THEN** the coverage job fails

### Requirement: Property invariants

These invariants MUST be tested with generated inputs (`hypothesis`), each
referenced by its id:

| # | Invariant |
|---|---|
| P1 | Fold determinism: a shuffled event log folds to the same state |
| P2 | Fold idempotence: duplicating any subset of events does not change the state |
| P3 | Serialisation round-trip: `parse(canon(x)) == x` for every schema |
| P4 | Canonical stability: `canon(x)` is byte-identical across runs, platforms, and hash seeds |
| P5 | Id determinism: the same record yields the same id regardless of import order, file, or platform |
| P6 | Normalisation idempotence: `normalise(normalise(s)) == normalise(s)` |
| P7 | Alias acyclicity: any sequence of merges yields a resolvable, acyclic alias graph |
| P8 | Dedup symmetry: `score(a, b) == score(b, a)` |
| P9 | Merge convergence: two disjoint event sets applied in either order yield the same state |
| P10 | Staleness soundness: every decision not marked stale provably cannot change, checked against a brute-force reference |
| P11 | Count reconciliation: all PRISMA identities hold for any random review history |
| P12 | Effect-size monotonicity: increasing `m1` increases `d`; increasing `n` decreases `v` |
| P13 | Undo inverts: a decision followed by its undo folds to the pre-decision state |

P10 and P11 protect the product's central claims and MUST NOT be weakened to
make the suite pass.

_Source: `docs/spec/14-testing.md` §2_

#### Scenario: Staleness soundness property

- **WHEN** the P10 property test generates a random criteria change and decision set
- **THEN** every decision the engine leaves valid is one the brute-force reference proves cannot change

### Requirement: Golden parser fixtures

`tests/fixtures/exports/` MUST contain real or realistically malformed exports
from PubMed/MEDLINE, Ovid, EBSCOhost, Scopus, Web of Science, ProQuest, Cochrane
CENTRAL, ClinicalTrials.gov, EndNote, Zotero, and Google Scholar (via Publish or
Perish), each with a committed expected parse. Fixtures MUST include the
malformations that occur in practice (BOM, CRLF, missing `ER  -`, CP1252 smart
quotes, HTML entities, inconsistent continuation indentation, diacritics,
corporate authors, missing years, DOIs with trailing punctuation, an empty
title) and MUST be redistributable, with sources documented in
`tests/fixtures/SOURCES.md`.

_Source: `docs/spec/14-testing.md` §3_

#### Scenario: Parser change alters output

- **WHEN** a parser change alters the parse of a committed fixture
- **THEN** the golden test fails until the expected output is deliberately updated

### Requirement: Statistical validation

For every estimator, the native engine MUST reproduce committed `metafor`
fixtures to a relative tolerance of 1e-8 (1e-6 for iteratively fitted `ML`/`REML`
`tau^2`), generated by a committed R script so the suite runs without R; a
nightly job MUST regenerate them against current `metafor` and fail on drift.
Results MUST also match published worked examples (the BCG vaccine dataset;
Borenstein et al.; Hedges & Olkin; a Cochrane review with zero cells). Where
`strata` deliberately differs from `metafor`, the fixture MUST pin `metafor`'s
matching option explicitly with an explanatory comment; tolerance MUST NOT be
bumped to hide a convention mismatch. Numerical edge cases (`k = 1`, `k = 2`,
identical `v_i`, one dominant weight, `tau^2 = 0`, zero cells in every arm,
`r = 1`, `n = 3` for Fisher's z, very large `n`) MUST each produce the correct
value or a specific actionable error, never `NaN`, `inf`, or a silently wrong
number.

_Source: `docs/spec/14-testing.md` §4_

#### Scenario: Upstream convention change

- **WHEN** a new `metafor` release changes an estimator's output
- **THEN** the nightly `metafor-live` job fails on the drift

#### Scenario: Fisher's z with n = 3

- **WHEN** a correlation effect with `n = 3` is computed
- **THEN** a specific error is raised rather than a division-by-zero result

### Requirement: End-to-end scenarios

Each scenario MUST be a scripted run against a temporary git repository,
asserting on file contents, counts, and generated output:

| Id | Scenario |
|---|---|
| E2E-01 | The origin scenario: init, criteria v1, two imports, dedup, dual screening, add a criterion, assert the exact stale set, re-screen, assert the flow diagram reconciles and the amendment text is generated |
| E2E-02 | Two collaborators screening concurrently on separate clones, syncing repeatedly, ending identical with zero manual conflict resolution |
| E2E-03 | Full review to publication: import through analysis, PRISMA diagram, characteristics table, manuscript export, reproducibility package |
| E2E-04 | Criteria loosened: exclusions citing it go stale and inclusions do not |
| E2E-05 | A criterion retired after exclusions cited it; cascade and re-screen |
| E2E-06 | Cascading staleness: a title/abstract reversal orphans a full-text decision and an extraction, without deleting the extraction |
| E2E-07 | Deduplication after a late fourth import, earlier manual dedup decisions not re-raised |
| E2E-08 | Recovery: corrupt a derived file, truncate an event file mid-line, delete the cache, then `strata verify --fix` restores a valid repository |
| E2E-09 | Interrupted screening (SIGKILL mid-session), then resume with no lost decisions |
| E2E-10 | A repository created by an older schema version, migrated forward |
| E2E-11 | Import of a 50,000-record export, asserting performance targets |
| E2E-12 | Determinism: the full pipeline run twice from the same inputs on different platforms yields byte-identical generated files |

E2E-01 is the specification's acceptance criterion and MUST NOT be weakened.

_Source: `docs/spec/14-testing.md` §5_

#### Scenario: Origin scenario

- **WHEN** E2E-01 runs
- **THEN** adding the age criterion produces exactly the expected stale set, and after re-screening the flow diagram reconciles and the amendment text is generated

### Requirement: Fuzzing

`ingest.parsers` MUST be fuzzed nightly, seeded from the real fixture corpus. A
parser MUST never hang, exhaust memory, execute code, or crash with an unhandled
exception; it either parses or reports a `ParseError` with a line number.

_Source: `docs/spec/14-testing.md` §6_

#### Scenario: Mutated RIS input

- **WHEN** the fuzzer feeds a randomly mutated RIS file to the parser
- **THEN** the parser returns records and/or `ParseError`s with line numbers and does not raise

### Requirement: Usability testing

At each milestone, at least three usability sessions with researchers who have
not used the tool MUST be run and recorded with consent, and their findings
MUST drive a prioritised issue list. This is a release gate.

_Source: `docs/spec/14-testing.md` §8_

#### Scenario: M2 release

- **WHEN** M2 is prepared for release
- **THEN** three sessions have tested whether users understand and trust the staleness report

### Requirement: Every change carries its tests

A pull request that changes behaviour MUST NOT merge without a test that would
have failed before the change. In particular, each kind of change MUST carry:

| Change | Required test work |
|---|---|
| Bug fix | A regression test that fails on `main` and passes with the fix |
| New normative requirement | At least one test naming it by requirement id |
| New CLI command or flag | An integration test, an exit-code assertion, and a `--json` shape assertion where applicable |
| New event type | Fold cases, a JSON Schema, schema-failure cases, and inclusion in the P1/P2/P9 generators |
| New parser or CSV profile | A golden fixture with a realistic malformation, plus inclusion in the fuzz corpus |
| New estimator or effect measure | A `metafor` fixture comparison, a published worked example where one exists, and the numerical edge cases |
| Change to identity, normalisation, canonical serialisation, the fold, or staleness | New property-test cases and a schema-version review |
| New derived view or generated artefact | A determinism assertion and a regeneration round-trip |
| New guardrail or error code | A test that it fires, and a test that `--force` bypasses it and records the bypass |
| Performance-sensitive change | A benchmark case if the path is not already covered |
| Documentation only | None, but specification integrity checks still run |

_Source: `docs/spec/14-testing.md` §10.1–§10.2_

#### Scenario: Bug fix without a regression test

- **WHEN** a pull request fixes a bug but adds no test that fails on `main`
- **THEN** it does not merge

### Requirement: Diff coverage

Changed lines MUST be at least 95% covered, and changed lines in the five
critical modules MUST have 100% branch coverage with no exemption. A deliberate
exclusion MUST use an inline `# pragma: no cover` with an explanatory comment.

_Source: `docs/spec/14-testing.md` §10.4_

#### Scenario: Under-covered pull request

- **WHEN** a pull request's changed lines are 90% covered
- **THEN** the coverage job fails

### Requirement: Requirement traceability

Every identified requirement — P1–P13, E2E-01 to E2E-12, and the `E_*`
cross-schema error codes — MUST have at least one test naming it with
`@pytest.mark.req(...)`. A CI step MUST collect the markers and publish a report
of uncovered requirements as a build artefact; once every current requirement is
covered, an uncovered requirement MUST become a gate failure rather than a
warning. New identified requirements get an id when written.

_Source: `docs/spec/14-testing.md` §10.5_

#### Scenario: Traceability report

- **WHEN** the traceability job runs
- **THEN** it lists every identified requirement with the tests naming it and flags those with none
