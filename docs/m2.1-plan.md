# M2.1 ("Project wiki and local MCP server") — sub-objective plan

Not part of the specification in `docs/spec/` (design content executed
once) — this is a working implementation-tracking note, kept outside
`docs/spec/` deliberately so it isn't subject to that tree's own
document-map/link-integrity checks (`scripts/check_docs.py`). Modelled on
`docs/m1-plan.md`/`docs/m2-plan.md`.

Unlike M0–M6, M2.1 has no single acceptance checklist and no "done" state
— per `docs/spec/15-roadmap.md`, it started the moment M2 shipped and runs
continuously alongside M3+. This file is a running log of what's landed so
far, not a status table with a finish line.

## What M2.1 covers

Per `docs/spec/15-roadmap.md`'s M2.1 entry: a GitHub Wiki (its own
versioned git repository, `strata.wiki.git`) covering the audience-facing
documentation set from `docs/spec/13-nonfunctional.md` §8, kept live going
forward via a PR-template checklist item rather than deferred to M6; and a
local, stdio MCP server exposing read/analysis/preview tools only, as a
fourth thin presentation layer alongside the CLI and web UI.

## Wiki

**Process — done, in the PR before this one** (`docs/spec: mark M2
complete in README, add install/getting-started, plan M2.1`, PR #14): the
"Wiki" checklist item in `.github/PULL_REQUEST_TEMPLATE.md` asking whether
a change adds or alters a user-facing command, web screen, or concept, and
whether the wiki was updated in this PR or a fast-follow.

**Content backfill — not started.** `strata.wiki.git` is a separate git
repository from this one (GitHub wikis are not reachable through the
normal GitHub REST/GraphQL surface this session's tools cover, only by
cloning `https://github.com/<owner>/<repo>.wiki.git` directly, and only
once the wiki feature has been enabled and initialised for the repo), so
it cannot be populated as part of a pull request against `strata` itself
the way every other change in this codebase is. This session scoped its
own work to the branch/PR workflow the task specified and did not attempt
to clone or push to a repository outside that scope without a separate,
explicit go-ahead. Left as an explicit, tracked gap for whoever next has
wiki-write access: back-fill quickstart, "first time using git", CLI
reference, web UI walkthrough, and concepts (staleness, criteria
versioning/direction, dedup, blinding) pages for what M0–M2 already
shipped, per the roadmap's own scope text — the same "reported, not
hidden" treatment M1/M2 gave their own out-of-scope items (EndNote/Excel
parsers, the usability session).

## Local MCP server — done (this session)

Spec: `docs/spec/15-roadmap.md`'s M2.1 entry, "Local MCP server" section.

Delivered: `src/strata/mcpserver/server.py` (`RepoTools`,
`create_mcp_server`), `strata mcp` in `cli/main.py`,
`tests/unit/test_mcpserver.py` (100% line+branch on
`mcpserver/server.py`), `tests/integration/test_cli_mcp.py`. New runtime
dependency: `mcp>=1.12` (resolved to the official MCP Python SDK's current
major version, 2.x — see the dependency-version note below).

- **A fourth thin presentation layer**, matching the relationship
  `web/routes.py` already has to `core`/`protocol`: `RepoTools` is a
  small class bound to one `repo_root` for the server process's lifetime,
  with one method per tool. Every method opens the repository fresh on
  each call (`strata.web.app.AppState.open_repo`'s own contract, reused
  here for the same reason: a human may edit the repository through the
  CLI or web UI between two MCP calls, and every read should reflect the
  current working tree). No method mutates anything — there is no
  `core`/`protocol` call anywhere in this module that appends an event or
  writes a file.
- **Scope held to exactly the roadmap's list**: `status`, `why`, `log`,
  `records` (the `--filter` language), `criteria_diff`, and
  `preview_criterion_change_impact`. Nothing that records a screening or
  criteria decision is exposed, matching the roadmap's own reasoning
  verbatim ("a screening decision is an accountable human judgement
  call... a tool letting an agent record one unsupervised undermines the
  provenance chain"). `tests/unit/test_mcpserver.py`'s
  `test_create_mcp_server_registers_exactly_the_scoped_read_only_tools`
  pins the exact tool-name set as a regression guard against scope creep.
- **Tool registration is bound-method registration**, not a hand-written
  schema: `mcp.tool()(tools.status)` etc. — the SDK derives each tool's
  JSON parameter schema from the bound method's own signature (`self`
  excluded, as for any Python bound method) and its description from the
  method's docstring, so there is exactly one place each tool's contract
  is written down, not two kept in sync by hand.
- **Errors are deliberately re-raised as `mcp.server.mcpserver.exceptions.
  ToolError`**, not left as the underlying `core`/`protocol` exception:
  this SDK version (2.x) treats any exception other than its own
  `ToolError`/`ResourceError`/`MCPError` family as an unanticipated crash
  and redacts the message down to `Error executing tool <name>` before it
  reaches the client (logging the real exception server-side instead) —
  a deliberate security default, not a bug. An unknown record id, an
  invalid `--filter` expression, an out-of-range criteria-diff version
  range, and an unknown criterion id are all *anticipated* failures a
  human or an MCP-aware agent should see the real message for, so
  `RepoTools` catches each domain exception (`RecordNotFoundError`/
  `AmbiguousRecordIdError`, `FilterSyntaxError`/`FilterEvaluationError`,
  `CriteriaError`, `RescreenError`) and re-raises it as `ToolError(str(exc))`.
  Confirmed end-to-end over the real stdio transport in
  `tests/integration/test_cli_mcp.py::
  test_mcp_unknown_record_reports_a_tool_error_not_a_crash`, including
  that the session survives an anticipated failure and serves a
  subsequent call cleanly (a crash would have torn down the transport
  instead).
- **`strata mcp` is a plain, no-option CLI command**: repository
  resolution reuses the existing global `-C`/cwd-walk machinery
  (`_resolve_repo`) every other command already uses, exactly matching
  the roadmap's "no new infrastructure" framing — an MCP client spawns
  `strata -C <path> mcp` (or sets its subprocess `cwd`) the same way it
  would spawn any other local stdio server, and the same way a human
  would run `strata status` from within a checkout.
- **Dependency-version note**: `mcp>=1.12` on PyPI currently resolves to
  `2.2.0` — the SDK's `FastMCP` class was renamed `MCPServer` (now at
  `mcp.server.mcpserver.MCPServer`) between its 1.x and 2.x major
  versions, with the `ToolError`/crash-redaction behaviour above being one
  of the resulting API differences. This implementation targets 2.x
  rather than pinning `mcp<2`, matching this codebase's existing
  no-upper-bound dependency convention (`typer>=0.12`, `fastapi>=0.110`,
  etc., all kept current via Dependabot) rather than freezing against a
  superseded major version on day one.
- **Testing**: `tests/unit/test_mcpserver.py` drives `RepoTools` directly
  (17 tests: every tool's success path, every tool's anticipated-error
  path, a dataclass-shape equality check against `compute_status`
  directly, and a `preview_criterion_change_impact` check against the
  real `protocol.rescreen` function's own output plus a
  non-mutation-of-`criteria.yaml`-version check mirroring
  `test_rescreen.py`'s own precedent for that function) — 100%
  line+branch on `mcpserver/server.py`, no MCP protocol/transport
  machinery involved, the same "drive the logic, not the protocol" split
  `test_web_server.py` uses for `web/server.py`. `tests/integration/
  test_cli_mcp.py` (3 tests) drives a real subprocess with the MCP SDK's
  own client transport (`mcp.client.stdio.stdio_client` +
  `mcp.ClientSession`), the same "cannot use `CliRunner`, it blocks"
  reasoning `test_cli_serve.py` documents for `strata serve` — confirming
  the real stdio JSON-RPC handshake, tool listing, a real tool call
  against a real repository, and the crash-vs-anticipated-error behaviour
  above, none of which the unit-level tests can reach.
