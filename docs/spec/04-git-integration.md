# 04 — Git integration *(normative)*

`epic` is a front end to git. This document specifies exactly how it drives git,
what it writes into history, and how it keeps merges from ever reaching the user.

## 1. Posture

**Git is never the user interface.** A user who runs only `epic` commands must
never see a merge conflict marker, a detached HEAD, a rebase prompt, or the word
"upstream". A user who *does* know git must find an ordinary, well-formed
repository they can branch, diff, blame, and review with standard tools.

`epic` MUST NOT wrap git so tightly that manual git use corrupts the repository.
Every invariant is restorable: `epic verify --fix` regenerates all derived files
and re-links event chains after any amount of manual git surgery.

## 2. Commit discipline

### 2.1 One operation, one commit

Every mutating `epic` command produces exactly one commit, unless `--no-commit`
is passed (which stages nothing and leaves the working tree dirty for the user to
handle). Batched screening is the exception and is specified in §2.4.

### 2.2 Structured commit messages *(normative)*

```
screen(title-abstract): exclude 42 records under new criterion EXC-07

Re-screened the 180 records flagged stale by the v3->v4 criteria change.
42 were excluded under the new age criterion; 138 retained.

Epic-Op: screen
Epic-Stage: title-abstract
Epic-Actor: ethan
Epic-Records-Affected: 180
Epic-Decisions: include=138 exclude=42
Epic-Criteria-Version: 4
Epic-Criteria-Digest: sha256:9f1c2a...
Epic-Events: ev_01j9x7m2q4h8s0v3n5k1t6w2yb..ev_01j9x7p0r1k3m5n7q9s1u3w5yd
Epic-Pool-Delta: -42
Epic-Schema-Version: 1
```

- **Subject line**: `<op>(<scope>): <summary>`, imperative, <= 72 characters,
  generated by `epic` from what actually changed. Never typed by the user.
- **Body**: the user's rationale — the "why". Wrapped at 72 columns.
- **Trailers**: machine-readable, `Epic-`-prefixed, one per line, RFC-822 style.
  These are what make the history queryable and what `epic prisma` and
  `epic report` read to generate the protocol amendment log.

`Epic-Op` values match the event types in
[02 §4.4](02-repository-format.md), plus `init`, `import`, `migrate`, `sync`,
`analyze`, `report`.

A commit-msg hook MUST validate the trailer block and reject a malformed one.

### 2.3 Eliciting the rationale

When `git.require_rationale` is true (the default), a mutating command MUST
obtain a rationale before committing. The prompt is specific to the operation and
tells the user what changed, so the answer is about *why*:

```
$ epic criteria edit EXC-03

  You tightened EXC-03 ("Non-English publication").

  This invalidates 180 of 1,204 screening decisions:
    138 previously INCLUDED at title-abstract  (a tightened criterion may now exclude them)
     42 previously EXCLUDED citing EXC-03      (the grounds changed)
    the other 1,024 decisions remain valid.

  Why did you make this change? (This goes in the permanent record and in your
  manuscript's protocol-amendment section.)
  > _
```

Rules:

- The rationale MUST NOT be empty, MUST NOT be whitespace, and MUST be at least
  12 characters. `epic` MUST reject `.`, `x`, `fix`, `update`, `wip`, and
  `asdf` (a shipped stop-list) with a message explaining why this matters.
- `--why "<text>"` supplies it non-interactively.
- `--why-file <path>` reads it from a file, for long amendments.
- In a non-interactive context (CI, a script) with neither flag, the command MUST
  fail rather than invent one.

### 2.4 Batched screening commits

Committing once per screening decision would produce thousands of commits and
make history unreadable. Instead:

- Decisions are appended to the event log immediately (so nothing is lost if the
  process dies) but left uncommitted.
- A commit is created when the user ends a screening session, when 200 decisions
  accumulate, or after 15 minutes of inactivity, whichever comes first.
- The rationale prompt for a routine batch is skipped; the generated message
  summarises the batch (`screen(title-abstract): screen 200 records (183 exclude, 17 include)`).
- A batch that contains any decision *contradicting* a previous resolved decision
  MUST prompt for a rationale, because that is a change of mind and the record
  should say why.

## 3. `.gitattributes` *(normative)*

Written by `epic init`:

```gitattributes
* text=auto eol=lf

events/**/*.ndjson     merge=union    -diff=nodiff
records/records.ndjson merge=epic-records
records/aliases.ndjson merge=union
derived/**             merge=epic-regenerate linguist-generated=true
reports/**             merge=epic-regenerate linguist-generated=true
analysis/results/**    merge=epic-regenerate linguist-generated=true
imports/*/raw/**       -merge -diff        # immutable; a conflict here is a bug
*.svg                  -diff
```

### 3.1 Merge drivers

Merge driver *definitions* live in `.git/config`, which is not committed, so
`epic init` and `epic doctor` MUST install them locally:

```ini
[merge "epic-regenerate"]
    name = epic: discard both sides and regenerate
    driver = epic merge-regenerate %O %A %B %P
[merge "epic-records"]
    name = epic: union-merge records by id
    driver = epic merge-records %O %A %B %P
```

`epic doctor` MUST detect missing drivers and offer to install them. A clone made
by someone who has not run `epic doctor` still works — git falls back to the
default driver and produces conflicts in `derived/`, which `epic sync` then
resolves by regeneration. The driver is an optimisation, not a correctness
requirement.

**`epic merge-regenerate`** ignores all three inputs, writes nothing, and exits
0; `epic sync` regenerates the file afterwards. This is safe precisely because
these files are never read as input.

**`epic merge-records`** performs a three-way merge keyed by record `id`:
- id present on one side only: keep it.
- id on both sides, identical: keep it.
- id on both sides, differing: merge field-wise. `epic.sources` is a set union.
  For scalar fields, if one side equals the base, take the other side. If both
  changed, apply `dedup.source_trust` precedence; if still tied, take the longer
  value for `abstract` and the lexicographically smaller value otherwise, and
  emit a `record-amend` event recording that an automatic resolution happened.
  Automatic resolution is always reported in `epic sync` output, never silent.

## 4. Hooks

`epic init` sets `core.hooksPath = .epic/hooks` so hooks are versioned and every
collaborator gets them on clone.

| Hook | Action | Failure |
|---|---|---|
| `pre-commit` | `epic verify --fast` (schemas, chains, dangling refs, derived drift) | blocks the commit |
| `commit-msg` | validate `Epic-` trailers when `commit_style = "structured"` | blocks the commit |
| `post-merge` | regenerate derived files, then `epic verify` | warns |
| `post-checkout` | invalidate `.epic/cache` if HEAD moved | never fails |

`--fast` MUST complete in under 2 seconds on a 50,000-record repository; the full
`epic verify` may take longer and runs in CI.

All hooks MUST be skippable via `EPIC_SKIP_HOOKS=1` for recovery scenarios, and
MUST print that the variable exists when they block an operation.

## 5. `epic sync` *(normative)*

The only sharing verb. Equivalent to fetch, merge, resolve, verify, push, but
with domain-level reporting.

```
$ epic sync

  Fetching origin ....................... done
  Incoming: 3 commits from sam
  Merging ............................... clean (union-merged 2 event files)
  Regenerating derived views ............ done
  Verifying ............................. ok

  What changed:
    Sam screened 412 records at title-abstract (387 exclude, 25 include)
    Pool: 1,204 -> 1,229 records at full-text
    New screening conflicts: 14   (run `epic adjudicate`)

  Pushing ............................... done
```

Algorithm:

1. Refuse to start if the working tree is dirty; tell the user to commit or stash
   via `epic`.
2. `git fetch <remote>`. Retry network failures up to 4 times with exponential
   backoff (2s, 4s, 8s, 16s).
3. If no divergence: fast-forward, regenerate, verify, done.
4. Merge (or rebase, per `git.sync_strategy`). Union-merged event files and
   regenerated derived files should resolve automatically.
5. **Normalise merged event files**: sort each by `(ts, id)`, drop exact
   duplicate `id`s, re-link the `prev`/`digest` chain, and append a `relink`
   event describing the rewrite.
6. Regenerate every derived file; `git add` them.
7. `epic verify`. On failure, abort the merge (`git merge --abort`), restore the
   pre-sync state, and report precisely what failed. **Never push an
   unverifiable repository.**
8. Commit the merge with a generated message and `Epic-Op: sync`.
9. Push with `git push -u origin <branch>`, with the same retry policy as step 2.
10. Report domain-level consequences, as shown above.

If step 4 produces a genuine conflict in a human-authored file (two people edited
the same criterion definition, or the same `question.md` paragraph), `epic` MUST
present it in domain terms and offer: keep mine, keep theirs, or open an editor.
It MUST NOT show raw conflict markers unless the user chooses the editor.

### 5.1 Why dual screening never conflicts

Each reviewer writes only to `events/screen/<stage>.<their-handle>.ndjson`. Two
reviewers screening the same 2,000 records touch disjoint files. The union driver
handles the case of one reviewer syncing from two machines. Disagreement between
reviewers is therefore *never* a git-level event — it appears in
`derived/conflicts.tsv` and the adjudication queue, which is where a
methodologist expects to find it.

This is the single most important structural decision in the format, and any
change to file sharding MUST preserve it.

## 6. Provenance queries

### 6.1 `epic why <record-id>`

Reconstructs the full history of one record from the event log plus git history:

```
$ epic why rec_3kq8v1r0zx2m4a7b

  Cepeda et al. (2008). Spacing effects in learning...
  Psychological Science, 19(11), 1095-1102.  doi:10.1111/j.1467-9280.2008.02209.x

  Current state:  INCLUDED (full-text) -> study std_7x2k9m1p3v5r8t0w

  2026-03-04  imported          S-01-medline (Ovid MEDLINE), row 412
  2026-03-04  imported again    S-02-embase, row 88  -> absorbed rec_9m2p0000000000ab
                                  score 1.00 (exact DOI)
  2026-03-07  screened  ethan   include   (criteria v3)
  2026-03-08  screened  sam     include   (criteria v3)
              -> resolved INCLUDE at title-abstract
  2026-03-19  criteria change   v3 -> v4  (EXC-07 added)
              -> decision marked STALE: a new exclusion criterion applies
                 commit 4f1a2b9 "Add age criterion after pilot extraction"
                 rationale: "Pilot extraction showed 9 of 40 studies used
                 child samples, which our question does not cover."
  2026-03-20  re-screened ethan include   (criteria v4)
  2026-03-20  re-screened sam   include   (criteria v4)
              -> resolved INCLUDE, no longer stale
  2026-03-28  retrieved         via institutional access, version of record
  2026-04-02  full-text ethan   include   (criteria v4)
  2026-04-02  full-text sam     include   (criteria v4)
  2026-04-03  grouped           into study std_7x2k9m1p3v5r8t0w
  2026-04-11  extracted         ethan, sam -> reconciled by ethan
              contributes 2 effects to analysis `primary`
```

Each line MUST cite the event id and, with `-v`, the commit that carried it. This
output is the answer to a peer reviewer's "why is this paper in your review?",
and it is generated, not remembered.

### 6.2 `epic log`

A domain-level `git log`: reads `Epic-` trailers and renders history as a list of
methodological events rather than commits. `--criteria` filters to protocol
changes, `--stage` to one screening stage, `--actor` to one person.

### 6.3 `epic diff <ref>..<ref>`

Domain-level diff between two points in history:

```
$ epic diff v1-protocol..HEAD

  Criteria:   v1 -> v4  (2 added, 1 tightened, 1 retired)
  Records:    +1,882 identified   (-419 duplicates)
  Pool:       1,204 -> 1,229 at full-text  (+67 entered, -42 left)
  Included:   38 -> 41 studies
  Primary:    g = 0.42 [0.31, 0.53] -> g = 0.38 [0.28, 0.48]
              I2 = 61% -> 58%,  k = 38 -> 41
```

The last line is the payoff of committing `analysis/results/`: a reviewer can see
exactly what a protocol change did to the headline number.

## 7. Repository hygiene

- **Size.** Raw exports are text and compress well; a 50,000-record review should
  stay under 200 MB. `epic doctor` warns above 500 MB and suggests `git gc`.
- **Full texts.** Never committed (see [13 §6](13-nonfunctional.md)). Teams that
  have cleared the rights to share PDFs internally MAY set
  `fulltext.track = "lfs"`, which `epic` supports but does not recommend and
  never enables by default.
- **History rewriting.** `epic` MUST NOT rewrite published history. There is no
  `epic amend` for a pushed commit. A mistake is corrected by a new event and a
  new commit, which is also what research integrity requires.
- **Branching.** `epic` works on whatever branch is checked out. Teams that want
  protocol changes reviewed before adoption can use ordinary pull requests;
  `epic` SHOULD document this pattern but MUST NOT require it.
